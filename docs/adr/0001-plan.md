# Plan — ADR 0001 load-aware backups

Status: Draft (huddle 2026-10-02).

## What the reference tools do (and what we take)

| tool | concurrency | overrun | load / window | resource caps | we take |
|---|---|---|---|---|---|
| pgBackRest | one backup per stanza, repo lock; `process-max` for parallelism | a second backup fails fast on the lock | none (cron decides) | `process-max`, `compress-level`, bandwidth via OS | fail-fast lock, compression knob |
| Barman | one backup per server, lock files; `barman cron` serialises | skip, logs "already running" | none | `network_compression`, `bandwidth_limit`, `parallel_jobs` | **bandwidth_limit**, skip-on-overrun |
| WAL-G | process per invocation, no queue | operator's cron problem | none | `WALG_UPLOAD_CONCURRENCY`, `WALG_NETWORK_RATE_LIMIT`, `WALG_DISK_RATE_LIMIT` | rate-limit knobs |
| RDS / Cloud SQL | one automated backup per instance | slot missed → next window | **user-set backup window**, default auto-picked low-activity 30-min slot | provider-side | **window + auto-pick from activity**, never move silently |
| k8s CronJob | `concurrencyPolicy: Allow/Forbid/Replace`, `startingDeadlineSeconds` | `Forbid` = skip | none | requests/limits | `overrun_policy` naming, starting deadline = `max_defer` |

No mainstream tool defers on live load; they rely on a **window**. So the window (suggestion) is the main
mechanism and the load gate is a safety net. That reorders the plan: window first, gate last.

## Team perspectives (short)

- **Architecture:** one worker, non-blocking child supervision is the core change; everything else rides on it.
  Don't build per-DB workers (max_worker_processes, N connections, no global view).
- **SRE:** biggest real-world harm is DDL stuck behind a dump's ACCESS SHARE locks, not CPU. `lock_timeout` +
  long-job doctor check ship first. Overrun default must be `skip` (CronJob `Forbid`).
- **Postgres:** nice on pg_dump doesn't reach the backend doing COPY; say so. Sampling `pg_stat_database` is cheap;
  `pg_stat_activity` per tick fine. PG 13 lacks some columns — test on 13–18.
- **Security:** `pgbx.cancel()` and `server_queue` must respect existing grants (viewer vs owner); no new
  superuser surface. ioprio_set needs no privilege for lowering.
- **Testing:** pgbench-driven e2e is slow; gate tests use low thresholds + `poll_seconds=5`. Bench is manual on
  self-hosted runners.
- **Product:** users want one sentence: "backups run in your quietest hour, never more than one at a time, and
  never block your app". Status/doctor must show *why* a job is waiting.
- **Skeptic:** the load gate adds RPO risk and tuning burden for little gain once window + caps exist. Ship it
  `off`, prove value in shadow, or drop it.

## Risks

- M2 changes the heart of the worker: SIGTERM, restart-recovery (`state='running'` → failed) and orphan-upload
  abort must keep working with children outliving a tick. Mitigation: keep job state in history, add a crash e2e.
- Extension upgrade path: new tables/columns via the existing `update_extension()` per DB; test 0.x → 0.x+1.
- Two lanes double peak load during restore; that's why `restore_lane` is a setting.

## Decisions (owner, 2026-10-02)

1. Load gate ships **shadow by default**, visible to clients (`pgbx status` / `pgbx load`, UI); teams switch it
   `on` per database. M6 and M7 merge into one release with default `shadow`.
2. Suggested schedule is **never auto-applied**; always shown with a copyable `configure()` call, CLI `--apply`
   (prompted) and a UI Apply button. `pgbx.suggest_auto_apply` dropped.
3. Overrun: **`skip` with a max-gap guard** (`overrun_max_gap = 1.5` × interval). `catch_up` stays as an option.
4. Time estimates on every job create and live progress (§4), owner request.
5. Restore lane: **on by default** (owner, 2026-10-02); `pgbx.restore_lane=off` for small servers.
